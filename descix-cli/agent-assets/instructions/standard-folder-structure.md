# Standard DeSciX Workspace Structure (Mono-Repo)

This document defines the canonical folder structure for DeSciX workspaces. Following this structure ensures consistency, discoverability, and seamless integration with platform tools.

## Workspace Hierarchy

DeSciX uses a "Mono-Repo" style structure where multiple communities and apps can coexist in a single workspace.

```
/ (Workspace Root)
├── .descix/
│   ├── workspace.json          # Workspace configuration (maps communities/apps)
│   └── wallet.json             # Developer credentials (DO NOT COMMIT)
│
├── [Community_ID]/             # Community Folder
│   ├── community_assets/
│   │   ├── icon.png
│   │   └── description.md
│   │
│   └── [App_ID]/               # App Folder
│       ├── assets/             # App Metadata
│       │   ├── app_description.md
│       │   ├── icon.png
│       │   └── system_instructions.md (AI Persona)
│       │
│       ├── .descix/
│       │   └── manifests/
│       │       └── General.json    # Corpus manifest — names the KB's git-tracked sources
│       │
│       ├── kb/                 # Knowledge Base content — OPTIONAL location, any path works
│       │   ├── staging/        # (if using Drive) Local files to push to Drive
│       │   │   └── new-doc.pdf
│       │   └── General/        # (if using Drive) Converted markdown from `descix drive pull`
│       │       └── *.md
│       │
│       ├── site/               # Frontend UI (Optional)
│       │   ├── index.html
│       │   ├── styles.css
│       │   ├── app.js
│       │   └── DeSciXAppSDK.js # The DeSciX bridge — GENERATED, do not hand-edit
│       │
│       └── microservice/       # Backend Logic (Optional)
│           ├── app.js          # Entry point
│           ├── Dockerfile
│           ├── package.json
│           ├── scripts/
│           └── services/       # NOT src/ — see below
│               ├── utils.js    # Config bootstrap — read this first
│               ├── apiFront.js
│               └── commandHandlers/
```

## Folder Purposes

### Root Level
- **`.descix/workspace.json`**: The source of truth for which apps are active in this workspace. Generated by the PWA Setup Flow.
- **`.descix/wallet.json`**: Your authentication credentials.

### Community Level (`[Community_ID]/`)
Contains all apps belonging to a specific community.
- **`community_assets/`**: Metadata for the community itself (branding, description).

### App Level (`[Community_ID]/[App_ID]/`)
Self-contained folder for a single application.

#### `assets/` - App Identity
- **`app_description.md`**: Public description for the App Store.
- **`system_instructions.md`**: Instructions for the AI Agent that interacts with users of this app.
- **`icon.png`**: App Icon.

#### `.descix/manifests/<KB>.json` - Corpus Manifest
**This is what makes a KB syncable — not any folder's existence.** It names the git-tracked
path(s) `descix kb corpus sync` walks, chunks and upserts to Pinecone. No manifest means nothing
to sync, regardless of what is under `kb/`.

#### `kb/` - Knowledge Base content (optional convention)
There is no required KB folder. `kb/` is one common place to keep content, especially if you also
use Drive-based authoring:
- **`staging/`**: Place raw files here (PDFs, images) to push them to Drive via `descix drive push`.
- **`General/`**: Files pulled from Drive and converted to Markdown via `descix drive pull`. Still
  needs to be named as a source in the corpus manifest to be indexed — pulling alone does not sync.

**CLI-Centric Processing (Git Mode):**
```bash
descix drive push      # (optional) Push staging/ -> Drive
descix drive pull      # (optional) Pull Drive -> local markdown, converted
# Commit the markdown, name its folder in .descix/manifests/<KB>.json, then:
descix kb corpus sync  # Walk the manifest's sources, chunk what changed, upsert + purge in Pinecone
```

#### `site/` - Frontend
- Contains the static website or Single Page Application (SPA).
- **`index.html`**: Entry point.

#### `microservice/` - Backend
- Contains the server-side logic.
- **`Dockerfile`**: Defines the runtime environment.
- **`services/`**: Service code. **There is no `src/` directory** in a scaffolded
  microservice — the entry point is `app.js` at the root and the code lives under
  `services/`, with `services/utils.js` as the config bootstrap over `@descix/cloud-core`.

## Configuration Files

### `.descix/workspace.json` (Root) — v2.1, the only supported format

```json
{
  "version": "2.1",
  "env": {
    "environment": "DEV",
    "apiUrl": "https://dev.descix.net",
    "products": [
      { "appId": "my-dao-governance", "communityId": "my-dao", "localPath": "my-dao/governance", "kbId": "General" },
      { "appId": "my-dao-treasury", "communityId": "my-dao", "localPath": "my-dao/treasury", "kbId": "General" }
    ]
  }
}
```

Written by CLI verbs only — `descix config init`, `descix app init`, `descix app set-site`,
`descix app set-port`. A `communities`-keyed block with no `env` block is the removed v1 shape and
is refused on load: `v1 workspace format is not supported. Migrate to v2.1.`

**Sync mode:** The CLI only performs **git-mode** operations (local files → corpus manifest →
Pinecone, via `descix kb corpus sync`). Drive-mode (Drive → GCS → Pinecone, fully server-side) is
PWA-only and is never triggered by the CLI. There is no per-app `sync_mode` switch in workspace.json
— using the CLI at all means git mode.

## Agent Workflow for Migration

When encountering an unstructured project:

1.  **Analyze**: Identify which files belong to Frontend (`site`), Backend (`microservice`), or Documentation (`kb`).
2.  **Scaffold**: Create the standard folder structure if missing.
3.  **Move**: Relocate files into their respective folders.
4.  **Refactor**: Update relative import paths in the code to reflect the new locations.
5.  **Update Config**: Ensure `workspace.json` has the correct app mappings.
